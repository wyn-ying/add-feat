# delivery 撰写规范

日期：2026-11-01。2026-11-03 修订：补充标杆样例、版本与基线收尾节、写前重跑、测试资产历史结论、验收矩阵衔接、exhausted/人工接管场景。状态：add-feat 交付节点写作要求。适用范围：最终交付草稿；项目规则优先决定命名、版本、批准与提交策略。

## 1. 定位与输入

delivery 是**按工程主题重组的版本交接参考**，不是需求复印件、末轮 dev、审计 JSON、聊天结束语或测试成绩单。目标读者不读会话及全部过程报告，也能理解交付了什么、如何工作、如何验证、还缺什么。

- **标杆样例**：对齐本项目最近一次公认优秀的产品交付的详细程度与组织方式（没有则按本规范自足展开）。只借鉴结构标准与表达方式，内容、数字与状态一律换成当前任务的事实，不得复制。

- plan 回答“批准要做什么”；dev 记录“每轮实际做了什么及红绿证据”；audit 记录“核验出了什么问题、哪些结论有效”；delivery 综合这些输入，回答“这个版本最终留下了怎样的工程成果”。
- 先读任务 README 的有效批准依据及适用 plan（含经批准补充）；不得按最大轮次、日期或文件是否存在推定批准。
- 盘点**全部适用轮次**的 dev/audit：提取最终保留的实现、重要修复、未覆盖项和结论变化。再用实际代码、契约、迁移、测试和可信 diff 核对；首轮声明不自动等于最终事实。
- 先做事实清单：主题／计划要求／最终实现／测试与审计证据／状态与限制。草稿可以不展示整张工作表，但重要交付声明须有可定位来源。
- 冲突时查证并说明；不能复制历史错误，也不能抹去旧不通过结论。缺证据写“未核实”，不从设计推导实现，不为丰富报告编造参数、字段、测试数量或审批。

## 2. 推荐正文框架（按任务适用性展开）

### 一、交付身份、范围与结论

写日期、任务/版本、适用范围、实际批准基线及确认依据、关联权威设计、代码状态。明确“AI 验收通过，未经人工确认”；实现完成、技术检查通过、独立审计通过、人工验收、已提交、已部署分别陈述。给已交付/未交付能力概览，不能把桩、预留表和未来接口算作完整功能。

### 二、架构、模块与接入

说明模块职责、代码入口、调用和依赖关系、应用组装、前后端接入、运行开关与失败行为。解释新功能怎样进入已有系统；不只罗列文件名。仅列本任务新增/变化/接入必需的配置，标实际默认值与约束并引用权威来源；不复制全项目配置。

### 三、接口与数据契约

按公开 HTTP、内部应用接口、客户端调用分别组织。给实际路径/方法/前缀/鉴权、关键请求响应字段及校验、状态与错误、版本及幂等约定。重要歧义给脱敏示例。明确不公开的数据和调用权限，不把内部接口写成 HTTP 能力。权威设计链接用于查全量定义，但不能用一个链接代替交接必需的摘要。

**调用方交付界面（用户明确要求时必备）**：撰写前询问并按服务性质推荐，记录用户决定及依据；不是通过猜测替用户确认。按实际交付版本列出所有对该调用方开放或改变的接口：用途、方法与路径/前缀、鉴权和权限、请求头、字段类型/必填/默认/约束、响应字段及可空性、脱敏的完整信封示例；列可达 HTTP 状态和业务错误码、触发条件及调用方处理；适用时说明幂等、重试、版本冲突、分页、异步/乱序、可见性和隐私。给出调用时序、依赖与环境获取方式，并标注未实现、mock、未验证、未部署和待确认项。逐项核对代码、测试与权威设计；歧义如实记录，不虚构部署地址、凭证或契约。内部接口与公开接口分开。纯内部工作用户选择不需要时，记录原因，但仍保留项目规则要求的必要接口摘要。

### 四、存储、归属与迁移

说明介质/schema、表或结构的职责、关键字段/约束/索引、归属、版本、生命周期、隐私载荷和删除策略。给实际 migration/revision 关系、新库初始化与存量升级区别、兼容/回填及回退或前向修复边界；标清仅在隔离测试库验证、尚未对业务库执行。不照抄 DDL，也不声称测试迁移等于生产迁移完成。

### 五、核心处理逻辑与一致性

按最终业务流程讲输入→校验/鉴权→外部调用→事务写入→响应/刷新。重点解释原子性、并发、版本冲突、幂等重试、失败/降级、删除与迟到请求等适用机制。把多轮修复吸收为最终不变量及其理由，而不是按 r1…rN 复制流水账；保留关键问题→修复机制→回归测试的简短映射。

### 六、客户端/UI 行为（适用时）

说明入口与组件、加载/空态/失败/已保存、校验与提示、冲突保留输入、保存刷新、取消/关闭/重开、旧异步响应的处理。区分自动化逻辑验证与真机视觉/设备授权验收。后端任务可说明“不涉及”及理由，不机械造章节。

### 七、安全、权限与隐私

汇总主体归属、授权、公开与私有投影、敏感信息处理、删除清理、外部供应商或审核桩的边界，以及失败是否会误报成功。写具体机制和剩余限制，不写“安全无问题”等保证。引用已核实的测试/审计证据。

### 八、验证资产、验收证据与代码绑定

- **对照 plan 的验收矩阵逐项给出结果**（通过/失败/未验证及原因）；plan 未矩阵化的旧任务按其"验收标准"节等效执行。
- **写前重跑全部冻结命令**，正文使用本次输出的数字与结论（passed/skip/耗时/退出码）；历史轮次数量只能作为"当时"证据引用，不得冒充本次结果。
- **测试资产自身的变更历史必须写入正文**：重建、合并、覆盖映射结论、误删与恢复事故——dev/audit 默认不入库，裸检出读者拿不到这些结论。
- 按能力列"行为/风险—测试文件或用例—实际证据—限制"；包含主要正常、边界、失败、并发和删除场景（适用时）。
- 列可复跑命令、**工作目录**、环境/依赖与安全前提、证据来源和执行时间（可获时）、实际结果与 skip/未运行原因。区分开发者自测、历史红绿、独立审计、闸门复检；旧轮数量不得冒充最终结果。
- 审计只给 pass/findings=[] 时如实引用，不能补造审计步骤。退出码 0 不等于所有边界或真机通过。
- 给实际可获的基线 commit、未提交差异范围/摘要或补丁标识、未跟踪交付依赖及最终审计引用；HEAD 不能单独代表未提交工作区。不编造 Git 摘要；无法取得则注明限制。
- 插件在正文之后追加本次可信复检的命令/退出码与工作区摘要；作者不可提前宣称尚未发生的最终复检通过。

### 九、未交付项、发布前提与交接导航

分清批准的非目标、残余风险、未验证事项和待人决策；给下一步及所需授权，不擅自开新任务。声明是否未提交/未部署、哪些真实供应商/设备/迁移尚未验证。附权威设计、入口代码、迁移、测试的有效链接，以及实际适用的 plan、关键 dev/audit。

过程报告默认不入库的项目，**交付正文必须自足**：关键机制、验证结果与限制不能只存在于将来不可达的 dev/audit 链接中。明确过程链接的本地属性，提醒未跟踪依赖；不擅自提交。

### 十、版本与基线（收尾节）

批准链与有效 plan、版本与轮次史（含闸门记录、追加预算、非闸门的人工轮次——各按实际）、当前基线 commit 或工作区摘要标识、未提交状态、入库策略（delivery 入库，dev/audit 留工作区）。

## 3. 撰写后的自检

1. 脱离会话，读者能否回答范围、接入、接口、存储、核心行为、验证和限制？
2. plan 的重要目标是否都有最终去向（交付证据／经批准排除／未完成），有没有把需求原文当实现证明？
3. 后续修复形成的关键机制是否已进入正文，而非只写在末轮报告？
4. 是否按主题组织，避免轮次流水账、命令堆砌、全量源码清单和为了篇幅复制设计？
5. 每项完成/通过声明是否有对应证据？桩、预留、未测、上线状态及独立性限制是否诚实？
6. 路径和相对链接是否存在并指向正确位置？命令工作目录、环境与代码状态是否明确？
7. 数字是否全部来自写前重跑？测试资产的历史变更结论（重建/覆盖映射/事故与恢复）是否已写入正文？

不以字数或固定表格数量衡量质量。小型纯文档任务允许合并章节；接口、存储、权限或跨端任务不能省掉相应工程内容。项目已有优秀交付可借鉴组织方式，不能复制其功能事实、历史数量或未经证实的状态措辞。

## 4. add-feat 执行方式及保证边界

协调者在 accept_ready 阶段、撰写前先询问用户是否需要调用方交付界面，按服务性质给出推荐并等待明确答复；再综合材料并自检，将**完整正文**放入 `final_accept {report:"<markdown>"}`。插件继续复跑冻结命令、核对工作区及过程文档，成功后附加状态水印和可信复检证据并写入已冻结的 delivery 路径。没有配置 delivery 的项目不强制提供正文。该人工询问由协调者执行，不是插件状态机强制校验。

插件强制“配置 delivery 则正文非空”，不再用需求摘要自动降级替代报告。**内容真实性、完整性及此框架的执行仍属协调者提示约束，不是独立文档质量审计**；非空校验不代表质量合格。正文写入失败可按闸门提示重试，不绕过写入或修改状态。

accepted 历史任务不会自动重写。若需由闸门登记同一验收成果的补写，另获用户落盘授权，通过 `revise_delivery {deliveryPath, report, userQuote, reason}` 写回本任务已登记的原 delivery；不新建版本、不改日期/路径、不重跑 final_accept。插件检查代码摘要和全部过程文档完整性，先将原字节及来源/哈希备份到 `~/.local/state/add-feat/delivery-revisions/`，再覆盖并重登记目标哈希，任务日志记录备份位置和用户原话。任务仍为 accepted，关闭时间、修复轮次和测试记录不变；正文标注修订时间并将测试标为“原验收证据（非本次重跑）”。备份失败不覆盖，写入失败保留备份并报告；不允许用此动作消除代码变化或过程文档完整性告警。原记录若与当前模板路径不符，拒绝该动作，不自动迁移。文件写入与状态保存尚非跨文件事务，也没有全局并发锁；补写期间应避免其他会话/外部工具修改同一工作区。

闸门拒绝或工作区任务槽已被其他任务占用，不等于永久禁止用户修改历史文件。任务已终态且项目规则允许时，用户可明确授权普通文档修订：不改状态文件、不伪造闸门登记，不覆盖历史结论；标明修订时间、当前代码及证据范围，历史测试为非本次重跑，并说明原验收不自动覆盖修订内容。直接编辑会使原过程文档哈希失配，后续 `revise_delivery`/`append_audit` 可能拒绝；动笔前告知用户该影响，不擅自修改活动任务的受保护文件。

任务**未走到 accepted**（如 exhausted 后人工接管验收）时，不存在闸门登记的 delivery：由人工（或经用户明确授权的会话）撰写定稿并手动放入任务目录，不经闸门、无完整性登记。此场景仍须满足本规范全部要求，正文标注“人工验收定稿”及其依据（终态复核记录等）；因无登记追踪，建议同步在任务 README 或终态后复核记录中互链。
