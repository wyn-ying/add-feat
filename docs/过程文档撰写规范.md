# 过程文档撰写规范（plan / dev / audit / README）

日期：2026-11-03。状态：add-feat 各角色与协调者的过程文档质量要求（用户确认版）。
适用范围：add-feat 工作流产出的全部过程文档；项目规则优先决定命名、版本与提交策略。
标杆：`docs/cowork/统一账号服务_2026-10-29/` 的证据链质量——继承其表达标准，不复制其旧流程（不恢复每轮建 plan，不把技术复核写成独立验收）。

## 0. 总原则

1. **报告必须能独立用于下一步工作**。读者不看聊天记录，也能回答：本轮依据哪个批准计划？处理了什么、没处理什么？具体做了哪些修改或核验？证据是什么、谁执行的？哪些问题关闭了、哪些还开着？下一节点做什么？
2. **不以篇幅判断质量**。简单问题可简写；并发、权限、隐私、迁移、删除、失败恢复等高风险问题必须展开。聊天汇报可以简短，归档正文不能因此缩水。用完整句子解释因果，不用只有原作者懂的压缩表达（如"红→绿、全清、保持"）。
3. **事实与结论分层**。区分：批准要求／开发者声明／实际执行结果（闸门证据）／静态审阅判断／独立审计结论／未验证推测。没有证据就写缺口，不编造内容填充章节。
4. **机械证据（哈希、退出码）尽量引用闸门输出**，不要求模型手抄长清单，更不能编造。

## 1. 三类文档共同的文首信息

- **身份**：任务名、版本/轮次、日期；
- **状态**：待确认／开发完成待审／审计不通过／阻塞／限定范围通过等，须与闸门真实状态一致；
- **适用依据**：实际有效 plan 的精确链接（修复轮写"沿用 plan vX.rY（链接）"），必要的批准补充与来源；
- **前序关系**：上轮 dev/audit 精确链接（首轮写"无"）；
- **范围**：本轮纳入与排除；
- **代码绑定**：可获得的基线/差异范围或闸门摘要标识；
- **权限边界**：是否提交、部署、业务库迁移——不混用这些状态。

## 2. plan：让人能批准，让开发者能施工

结构（按任务适用性展开，小任务可合并章节但保留要素）：

1. **需求依据与批准状态**：需求来源、已确认决策、未决项、权威设计与冲突处理。不得把"文件已生成"写成"已批准"。
2. **目标、范围与非目标**：交付能力清单 + 明确不做的能力；外部依赖未就绪、mock/桩、人工步骤必须显式。
3. **方案与关键行为**：模块职责与调用时序、接口/鉴权/错误/版本语义、存储归属/约束/生命周期/迁移、前后端状态与失败交互、幂等/并发/删除/防迟到等不变量。可引用权威设计避免重复，但不能只留"详见设计"使计划自身无法审批。
4. **实施步骤与依赖**：顺序、跨模块接入点、依赖就绪情况、遇缺口暂停哪部分。
5. **验收矩阵**：重要要求逐项映射验证方式——

   | 要求 | 场景及预期 | 验证方式 | 限制 |
   |---|---|---|---|

   写"测什么行为、期望什么结果"，不是罗列"测试并发、测试权限"。
6. **修改范围、命令、风险与文档方案**：allowedPaths、验收命令及工作目录、环境前提、风险、docRules。

普通修复轮沿用有效 plan，不新建（维持现行规则）。

## 3. dev（含首轮开发与修复轮）：证明本轮做了什么，不是宣布通过

1. **本轮结论与依据**：一句话结论 + 适用 plan/上轮 audit 链接 + 状态措辞（"已完成实现及自测，待独立审计"，不得写"验收通过"）。
2. **变更明细**：按能力（首轮）或问题编号（修复轮）组织——

   | 问题/能力 | 原行为及原因 | 本轮修改机制 | 文件/函数 | 契约影响 |
   |---|---|---|---|---|

   必须解释"为什么能修复/为什么这样实现"，不能只有文件列表。
3. **逐问题处理记录**（修复轮）：原问题与复现是否确认 → 实际修复 → 覆盖与未覆盖场景 → 定向测试结果 → 状态（已实现待审/部分完成/未处理/阻塞）。开发者可声明"修复完成待审"，**不能自行关闭审计问题**。
4. **红灯、绿灯与回归证据**：每组证据交代工作目录、命令、环境（隔离库/合成凭证等）、测试文件/用例、修复前真实失败及原因、修复后结果、全量回归的退出码/失败/跳过/超时。环境错误不算有效红灯；未保留红灯证据就如实说明，不事后补造。
5. **测试资产变更**（关键）：删除、合并、重写测试或明显改变断言时，必须附覆盖映射——

   | 原用例/行为断言 | 变更原因 | 新用例及对应断言 | 是否存在覆盖损失 |
   |---|---|---|---|

   判断依据是**行为断言是否保留**，不是数量。误清空、重建文件、证据丢失等事故必须单独披露。
6. **偏离、遗留与交接**：方案偏离及授权、设计回填位置、未解决项与风险、请审计者重点复核的部分。

## 4. audit：核验报告，不是问题数组

即使结论是 pass 也必须提供完整正文。结构：

1. **结论、范围与独立性**：依据与受检代码状态、是否参与本轮实现、通过/不通过/阻塞及理由、结论适用范围。
2. **核验方法与证据来源**：阅读了哪些实现/测试/设计、使用了哪些闸门真实结果、**已执行复现**（命令/脚本、容器环境、真实结果）与**静态审阅（未复现）**分开列出，不混写。不编造"独立实测"，但也不因此降低独立审阅要求。
3. **上轮问题复核表**——

   | 编号 | 开发者声明 | 本轮核验依据 | 处置（关闭/部分有效/未关闭/受阻） |
   |---|---|---|---|

   旧问题不得无解释消失；编号保持稳定。
4. **本轮问题详情**：每条实质问题含——编号与标题 → 严重度/复杂度（分开）→ 要求依据 → 定位 → 触发条件或复现方法 → 预期/实际 → 影响与边界（不夸大：故障注入证明存在缺陷分支 ≠ 生产已发生事故）→ 修复建议 → 关闭条件。**每条问题必须满足证据纪律之一（已复现并附命令与环境，或附可执行的验证方案与判定标准并注明"静态发现、未复现"）**；并发问题说明事务交错与共同资源；测试缺陷说明它无法证明哪个行为；区分实现缺陷/计划缺口/需人决策。
5. **已核验项与剩余限制**：本轮确认有效的关键机制及证据；不写"未发现问题所以绝对安全"。
6. **后续动作**：哪些进普通修复、哪些需人确认、哪些证据/环境问题单独处理。任务终态后的事后复核（如整体技术复核）经 `append_audit` 登记为下一空位轮次，正文必须标注记录性质，不改变终态与历史结论。

机器可读结论（verdict/findings）照旧输出，正文放 `report` 字段；两者矛盾以事实为准并说明。

## 5. README：任务导航，不是状态残影

由插件维护，至少包含：当前有效 plan 链接及批准依据、当前 v/r 与修复轮计数、各轮 dev/audit 链接、未关闭问题清单（编号+摘要）、最近代码/证据状态、delivery 链接与人工确认状态。状态措辞必须对应闸门真实结果（任务已 exhausted 不得写"审计进行中"）。README 不复制轮次详情，只做入口与状态。

## 6. 质量执行方式

- 协调者：按本规范撰写 plan；向各角色下发对应格式要求；收到报告先查缺项——缺项退回原角色补全（修复轮补文档**不消耗额外修复预算**，可要求原修复者补全正文后再 end_fix）。
- 开发者/修复者：返回可归档的完整 Markdown 正文，不是压缩聊天总结。
- 审计者：verdict/findings（机器可读）+ report（完整正文）同时返回。
- 插件：`end_audit` 无 report 拒绝；`end_dev`/`end_fix` 正文过于单薄拒绝（纯文档小任务允许简化但须说明依据与验证）；README 按导航模板服务端生成。
- 报告与结构化结论矛盾时先纠正再推进；不以"标题齐全"认定内容合格。
